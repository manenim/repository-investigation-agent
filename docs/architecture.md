# Context, verification and tool boundaries

Trace uses an explicit typed workflow: ingestion → retrieval → documentation → investigation → verification → persistence/export. These are application stages, not autonomous agents. The generation and verification calls use separate instructions and artifacts; they may use the same configured model and therefore have correlated errors.

The GitHub adapter constructs HTTPS routes on `api.github.com` itself. Input can choose only the allowlisted public repository and a validated ref or matching issue URL. User URLs are never passed to an HTTP client. Redirects are rejected. The adapter checks public repository identity, resolves a full commit SHA, reads its Git tree, bounds inventory and source size, and checks every downloaded blob against the tree's Git hash. It never clones, imports or executes target source. The model has no tools, filesystem, network capability or API keys in its input.

The retriever splits original source into overlapping 44-line chunks at 34-line intervals. Term extraction splits CamelCase and normalizes simple plurals. Lexical scoring weights term frequency and corpus rarity, with a modest source-code preference. A public-interface anchor is reserved; diagram questions also include the short diagram sources. Two chunks per file are considered before deferred chunks to reduce long-file dominance. Selection stops at ten chunks and the byte budget. Scores select context; they do not prove relevance or completeness. Annotated misses remain visible in evaluation results.

The analyst receives issue text and retrieved evidence as untrusted JSON data under fixed system instructions. Documentation produces architecture claims. Investigation produces observations, hypotheses, counter-evidence, proposals and questions. Every factual claim carries evidence IDs. The application supplies the actual citation metadata; a model cannot choose arbitrary external links. Source text and model output enter the UI through `textContent`, never raw HTML. Markdown export is plain text for human review; do not treat exported Markdown as trusted executable content.

Reference checks independently recompute stored blob hashes and compare repository, SHA, path, line bounds, excerpt and GitHub permalink. The semantic stage gets each claim paired with its own cited excerpts. It must return one verdict and exact supporting quotation per supported/plausible claim. Missing/duplicate judgments, bad citations, or missing/mismatched quotations fail closed. Hypotheses remain hypotheses even if the model says supported. Unverified proposed filenames are explicitly flagged rather than represented as existing source. Fix and validation plans remain proposals; no change or test execution is implied.

An exact quote proves that text occurs in the source, not that a claim follows from it. Compound assertions, diagrams interpreted as deployment evidence, external rendering claims and causality remain risks. Manual review is required and documented separately.

A SQLite row stores the original issue input, run metadata, intermediate stage artifacts and evidence, progress, final snapshot, verification results, usage and report. One asyncio worker consumes a four-slot queue. Admission is authenticated and globally bounded in SQLite. A 420-second deadline bounds a run. Failed runs return an explicit error without provider exception text, source prompts or secrets in logs. On restart, queued/running rows are marked failed; completed rows are preserved. There is no retry after restart and no exactly-once or distributed scheduling claim.

Only the application developer's own tests run in CI. The target repository's test files can be read as evidence of intended assertions, but their existence cannot establish that they pass.
